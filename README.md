# ExpenseFlow

**中小企業向け「支出と入金の予定を紐づける」キャッシュフローガバナンスツール**

ExpenseFlowは、経費精算の効率化と入金確認の自動化を一元的に行い、**「支出を承認する前に、入金予定を明確にする」**という業務ルールを実現するポートフォリオ向けMVPです。

## プロジェクト概要

### 背景と目的
中小企業では、経費精算（支出側）のデジタル化は進んでいる一方で、入金確認（収入側）の手作業が依然として大きな負担となっています。特に「支出の承認時点で対応する入金予定が登録されているか」をシステムレベルで管理できていないケースが多く、キャッシュフローの可視化とガバナンスに課題を抱えています。

ExpenseFlowは、この「支出と入金の予定の連動」という観点に特化し、既存の会計ツールでは十分にカバーできていない領域を補完することを目指します。

### ターゲット
- 従業員規模：おおよそ10〜50名程度の中小企業
- 利用者：経理・財務担当者、経営者
- 課題感：入金確認の手作業、支出承認時のキャッシュフロー意識の欠如、振込名義の管理負担

### 開発期間・方針
- 開発期間：1週間集中型MVP
- 方針：完璧を目指さず「動くもの」を最優先。後から拡張しやすい設計を意識
- ポートフォリオとしての価値：業務課題の理解力、セキュリティ意識、AI活用のバランスをアピール

## 主な機能（MVPスコープ）

### 1. 経費精算（支出側）
- 領収書・請求書のアップロード
- Claude VisionによるAI自動解析（金額、日付、取引先、税区分など）
- 承認ワークフロー（シンプルな多段階承認を想定）
- 支出承認時に「対応する入金予定」の選択を推奨・意識させる設計

### 2. 入金確認（収入側）
- 銀行明細のCSVアップロード
- AIによる自動マッチング（取引先名義・金額・期日・口座下4桁マスキングとの照合）
- 振込名義エイリアス登録（1つの取引先に対して複数名義を管理可能）
- 口座番号は下4桁のみマスキング保存（セキュリティと実用性のバランス）
- 入金期日管理と超過アラート

### 3. ガバナンス機能（差別化ポイント）
- 支出承認の際に「対応する入金予定」の登録状況を確認できるように設計
- 入金予定が未登録の場合の警告・確認フローを考慮
- 将来的に「入金予定未登録では承認不可」といったルール化も視野

### 4. セキュリティ・データ管理
- Supabase RLSによる組織（会社）単位のデータ完全隔離
- 口座番号は下4桁のみ保存し、マスキング表示
- 振込名義はエイリアスとして柔軟に管理
- 領収書画像は解析後に削除または非公開ストレージで管理（今後検討）

## 技術スタック

- **フロントエンド**：Next.js 15 (App Router) + TypeScript
- **UI**：Tailwind CSS + shadcn/ui（モダンで一貫性のあるデザインシステム）
- **バックエンド**：Supabase（認証・データベース・ストレージ・RLS）
- **AI**：
  - 領収書解析：Claude Vision（Anthropic）
  - 入金マッチング：カスタムロジック＋将来的にLLM活用を検討
- **デプロイ**：Vercel（フロントエンド）＋ Supabase（バックエンド）
- **その他**：Zod（バリデーション）、Recharts（簡易ダッシュボード）

## デザイン方針

- 全体の印象：**信頼感・効率感・モダンさ**を両立
- カラーテーマ：深いネイビー（信頼）をベースに、ティール（効率・先進性）をアクセントに使用
- レイアウト：レスポンシブ対応を前提に、PCでは横並びを活かした情報密度の高い表示、スマホでは縦積みで操作性を重視
- コンポーネント：shadcn/uiをベースに、必要最小限のカスタマイズで一貫性を保つ
- ダークモード：将来的な対応を視野に、ライトモードをメインに設計

## セキュリティ・コンプライアンス

- 個人情報保護法を意識したデータ最小化設計
- 口座番号は下4桁のみ保存（フル口座番号は登録不可）
- SupabaseのRow Level Security（RLS）で組織間データ漏洩を防止
- 本番運用を見据えた「暗号化・監査ログ・脆弱性診断」の追加を将来的に検討
